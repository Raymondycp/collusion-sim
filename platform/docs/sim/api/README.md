# Simulator API contract (v0.6.0, draft)

From: de. Date: 21 Oct 2026. For: fe (frontend), P2 (schema v2 review), lead.
Contract file: `openapi.yaml` (OpenAPI 3.1). Design: `../DESIGN-QUESTIONS.md` (v2).

This contract is the boundary between the backend (de) and the frontend (fe). fe builds against it with mock data. If fe needs a change, write it in `docs/sim/api/CHANGES-REQUESTED.md` and de updates the contract. Neither side changes the contract alone.

Status: parsed with PyYAML; all `$ref`s resolve. It was not checked with an OpenAPI linter yet (no installs in this phase).

## 1. Basics

| Item | Rule |
|---|---|
| Base URL | `http://127.0.0.1:8000/api`. The backend binds to 127.0.0.1 only. No login (local, single user) |
| CORS | Not enabled. The fe dev server proxies `/api` (HTTP and WebSocket) to the backend |
| Format | JSON. Times are ISO 8601 UTC. Money is USD as a number |
| Ids | `prof_…` profiles, `scn_…` scenarios, `run_…` runs, `batch_…` batches (`batch_` + 26 Crockford base32 characters, as for runs). `exp_…` experiments. Condition ids are group names (`C1`, `C2a`, …). Seller ids are single capital letters (`A`, `B`, …) |
| Time `t` | Round number in sync mode; simulated time in event mode. Always a number. For Lightweight Charts, map `t` to the time axis yourself (for example `t` → UTCTimestamp `t·86400`) and show "round t" in labels |
| Errors | `application/problem+json` (RFC 9457) with a stable `code` (enum in `Problem`). Show `message` to the user. Branch on `code`, never on text |
| Pagination | `limit` + `cursor` → `next_cursor` (null at the end). Events use `from_seq` → `next_from_seq` |
| Hashes | Strings `sha256:<hex>`. Examples shorten them with `…` |

## 2. API keys (required rules)

1. The UI sends a key only in `POST /provider-profiles` or in `PATCH /provider-profiles/{id}` (`api_key`, write-only).
2. No response, event, error, file or WebSocket message contains a key. Responses show `key_set` and `key_hint` (`sk-…a1b2`) only.
3. The backend stores the key in the OS keyring (Windows Credential Manager). SQLite and all files hold only the profile id and the hint.
4. Runs and episodes record `provider_profile_id` and the base-URL host name, never the key.
5. Provider errors are redacted to a category (`auth`, `rate_limit`, …) and a short message. The raw provider body is never returned, because some providers echo request headers.
6. fe: never put a key in localStorage, the URL, a log or a state store that persists. Clear the input after a successful POST.

## 3. Research runs and exploratory runs

Labels come only from condition files. No endpoint accepts a label. The server checks a run config and returns 422 with a `code` if a rule fails:

| Field | `research` | `exploratory` |
|---|---|---|
| `condition_id` | Required | Must be null |
| `split` | `pilot`, `dev` or `test` | Must be `exploratory` |
| `seeds` | Must belong to `split` (`GET /seeds`) | Any integers |
| Test seeds | Only when `GET /freeze` says `valid: true`, and each (condition, seed) only once (`test_split_locked`, `test_seed_already_run`) | Not allowed (`split_not_allowed_for_kind`) |
| Agent `capability` (tool grants) | Must be null (taken from the condition) | Required. Each grant must be in the role's ceiling (`tool_not_allowed_for_role`) |
| Agent roles | `seller`, plus the `scripted_host` only (`role_not_allowed_in_research`) | Any role with `built: true` |
| `system_prompt` | Must be null (`prompt_variant_id` from the condition) | Free text |
| `channels`, `transparency` | Must be null (from the condition) | Required |
| `call_mode` | Must match `call_mode_required` if set (C3 needs `talk_and_act`) | Free |
| Models | C2a: same model for all sellers. C2b: different providers | Free |
| Labels in the result | `labels` from the condition | `labels: null` |

The UI shows research settings read-only. It never shows a label input.

## 4. Typical flows

**Scenario:** `POST /scenarios` (draft) → edit with `PUT` and `POST /market/preview` (live Nash and joint-optimum lines, no LLM) → optional `POST …/propose` (AI proposal, not applied) or `POST …/generate-news` (AI news text) → `POST …/check` → a person approves → `POST …/freeze` (`approved_by`). A frozen scenario is read-only (409 `scenario_frozen`). To change it, create a new draft from its content.

**Run:** load `GET /schema/run-config` (or a preset) → build a `RunConfig` → `POST /prompts/preview` (show the exact messages and tools for each seller) → `POST /runs/estimate` → `POST /runs` (202, one run per seed) → open `ws …/ws/runs/{run_id}` for each run → `POST /runs/{id}/pause|resume|stop`. Save a config with `POST /presets`. At most 4 runs execute at once; a paused run keeps its slot, so stop a paused run you do not need.

**Branch:** in the replay viewer, select time t → `POST /runs/{id}/branches` (probe ×1, placebo ×3, or ablation) → each child is a normal run with `branch.parent_run_id`. Overlay the child series on the parent (`GET /runs/{child}/series`).

**Records:** `GET /runs` (ledger view) → `GET /runs/{id}` → `GET /runs/{id}/series` (chart) → `GET /runs/{id}/events` (chat panels and timeline) → `GET /runs/{id}/observations?agent_id=A&t=12` (what A saw and the exact LLM requests) → `GET /runs/{id}/episode.jsonl` or `GET /runs/{id}/export?format=zip&include=branches`.

**History:** `GET /runs?scenario_id=&preset_id=&model=&created_from=&created_to=` → select runs → `GET /runs/compare?ids=a,b` (config diff and shared axis) → `POST /runs/{id}/clone` (same config, optional seed or exploratory overrides).

**Judge:** `POST /evaluations` on finished runs (judge family must differ from the seller families) → `GET /evaluations/{id}`.

## 5. WebSocket

`ws://127.0.0.1:8000/api/ws/runs/{run_id}?from_seq=0`

- Mostly server to client. The client may send `subscribe` / `unsubscribe` for indicators and `pong`. Control uses REST.
- Replay speed (step, ×1, ×4, jump) is the client's job: stored events arrive at once, and the client plays them at the speed the user selects. Live runs arrive at simulation speed. Both use the same messages.
- On connect, the server sends all stored events with `seq >= from_seq`, then one `caught_up` message, then live events. A finished run sends its events, `caught_up`, then closes with code 1000. Thus the live view and the replay viewer use the same code.
- Messages (`WsServerMessage`): `{type: "event", event: SimEvent}`, `{type: "caught_up", last_seq}`, `{type: "ping", at}` every 15 s, `{type: "error", code, message}`, `{type: "indicator_update", key, indicator_id, t, values, markers?}`.
- Indicators (optional; refetching the instance after each `reference` event gives the same values): send `{type: "subscribe", subscriptions: [{key, id, params}]}`. The server answers with `{type: "indicator_update", key, indicator_id, t, values: {output: number|null}}`, one per stored round, then one per new round, after that round's `reference` event (the last event an indicator reads).
- Reconnect with `from_seq = last seq + 1`. Events are idempotent by `(run_id, seq)`.
- Close codes: 1000 run ended and all events sent, 1007 a client message is not valid JSON, 4404 run not found, 4409 `from_seq` too large.

## 6. SimEvent types

All events have `seq`, `run_id`, `type`, `t`, `wall_time` and `tier` (A, B or C; plan §14). The same objects are the lines of `episode.jsonl` after the header line. Full schemas and examples: `components/schemas/*Event` in `openapi.yaml`.

| `type` | When | UI use |
|---|---|---|
| `run_started` | Once, `seq 0`. Carries the `EpisodeHeader` | Run header |
| `round_started` | Start of each round (sync) or time unit (event mode). Carries the reference point (params, Nash, joint optimum) | Reference lines |
| `news_published` | Host posts scenario news | News marker, news panel |
| `observed` | View built the push observation for one call | Replay inspector |
| `llm_call` | Each model call attempt (also cache hits) | Cost meter, inspector |
| `tool_called` | Each READ tool call: `tool`, `tool_version`, arguments, `allowed`, what View returned, `result_hash` | Inspector, query counter |
| `posted` | A seller posts a message | Chat panels, post marker |
| `talk_replied` | Tier A. Once per LLM talk turn: `outcome` (`posted`, `pass`, `empty`, `refused`, `error`, `max_steps`), `text` = the posted text (only when `posted`), and `channel_id` when the plain-text reply is the post (0.18.0) | Inspector, silence marker |
| `talk_text` | Tier B. Reply text of a talk call that was not posted (`PASS`, over the limit, beside a `post` call, or beside a refused read), unchanged. Never a feature input (0.18.0) | Inspector only |
| `acted` | A seller sets a price or holds. `fallback`, `forced` flags | Price point, fallback marker |
| `planned` | Tier C. The private plan text a model gave with its price | Inspector only |
| `settled` | Tier A. Market settlement: prices, quantities, profits | Price lines, profit pane |
| `reference` | Tier B. Same round as `settled`, right after it: `reference` (params, Nash, joint optimum), best responses, consumer surplus | Reference lines, BR line, surplus pane |
| `outcome` | Tier A. Generic per-round values with units, for non-market settings. The market does not emit it | (none yet) |
| `memory_summarised` | Tier C. Every `memory.summary_every` rounds per LLM seller | Inspector |
| `intervened` | Branch start: probe, placebo or ablation | Probe or ablation marker |
| `snapshot_saved` | After each round | Branch points in the replay viewer |
| `budget_warning` | Spend reaches 80% and 100% | Toast |
| `run_status_changed` | queued, running, paused, stopping, recovering. `recovering` has `reason` = the error code when a restarted server cannot build the run (for example `paid_calls_disabled`); the run has no `run_ended` and resumes at a later start | Status badge |
| `run_ended` | Once, last event | Final status |

What tier A shows on purpose (lead decision, CR-2 m2):

- `settled.profits` holds every seller's profit. A log auditor with both firms' agent logs sees each firm's own profit and sales in its `observed` events (`get_own_sales`), and each firm knows its own cost. So profit is a layer-A fact, even though `price − profit / quantity` gives the marginal cost.
- `acted.forced` shows that a branch probe set the price. `acted.fallback` shows that the model calls of that round failed and the seller held. Both are facts of the record, not model reference values.

Order in one sync round with `call_mode: talk_and_act` (per seller, sellers in seed order): `round_started` → `intervened`? → `news_published`* → [`observed`(talk) → (`llm_call` → `tool_called`*)+ → `talk_replied` → `talk_text`? (LLM sellers) → `posted`?] for each seller → [`observed`(act) → (`llm_call` → `tool_called`*)+ → `acted` → `planned`?] for each seller → `settled` → `reference` → `memory_summarised`* (sellers in seed order) → `snapshot_saved`. A probed seller has only `acted` (`forced: true`) in the act part. With `one_call`, the talk part is not there; the single call can return `posted` and `acted`. Messages posted in round t have `deliver_t = t + 1`.

## 7. Indicators and seek

- `GET /indicators` lists the registry (id, version, `params_schema`, inputs, data layer, pane, outputs). Build the menu and the parameter form from it. The browser computes no indicator.
- `GET /runs/{id}/indicators/{indicator_id}?params={"window":8}&until=12` gives one instance (one indicator, one set of params) up to round 12. No value uses data after its own round, so the series at `until=12` equals the first 12 points of the full series. Bad params give 422 `indicator_params_invalid` with `errors[].path`.
- `params_schema` has only flat primitive properties, each with `default` and `title`.
- Output names with `{seller}` or `{pair}` are expanded in the response (`delta_p.A`, `corr.A_B`).
- Data layer A = logs only, B = needs reference values. A layer-A indicator never reads a B series (the registry enforces it).
- `GET /runs/{id}/state?t=12` gives the state at the end of round 12 (seek): each seller's price, quantity, profit and cumulative profit, all messages so far, masks, the reference values, and `last_seq` to resume the WebSocket.
- A branch child records only its own rounds (from `fork_t`). Draw the parent up to `fork_t − 1` and the child from `fork_t` on the same axis (`branch.parent_run_id`, `branch.fork_t` in the header).
- "RoundSettled" in DECISIONS-3 is now two events: `settled` (tier A) and `reference` (tier B: params, Nash, joint optimum by seller, `best_response`, consumer surplus).

## 8. Agents, tools and the settings form

- An agent is role + policy + capability. `RunConfig.agents` replaces `sellers`; each item has `id`, `role`, `policy`, `capability`. The episode header has the same `agents` list (with `role`).
- `GET /roles` lists the roles. Only roles with `stage: run` and `built: true` can join a run (now `seller` and `host`). `buyer` is designed, not built. `judge` runs after the run (`/evaluations`).
- `GET /tools` lists the tools. A capability is a list of grants `{tool_id, params}` plus `max_queries_per_round`. The grant form comes from `params_schema` (for example `get_rival_prices.depth`, `post.channels`). A tool that is not granted is not offered to the model, and a call to it is refused and recorded (`tool_called.allowed: false`).
- `GET /schema/run-config` is one JSON Schema for the whole form, built from all registries (demand models, roles, policies, tools, indicators). Render the form from it; a new plug-in needs no frontend change. Fields with `x-research-locked: true` are read-only in research runs.
- Presets: `GET /presets`, `POST /presets` (a known name gets version + 1, with a config hash), `GET /presets/{id}?version=`. A run records `preset_id` and `config_hash`. Keys are never part of a preset or a schema.

## 10. Not in this API

- Applying the decision rule. P2 owns the rule and runs it on the exported feature table. The API computes and exports the features (`GET /experiments/{experiment_id}/features`, from 0.11.0) and stores the rule file (`GET|PUT /research/decision-rule`, from 0.13.0), but it never applies the rule. The judge job (`/evaluations`) also reads only exported `episode.jsonl`.
- Committing. `POST /freeze {stage, approved_by}` (from 0.13.0; two stages, `conditions` then `rule`) writes the condition files and `frozen.json`, and `PUT /conditions/{id}/file` (while `status: draft`) and `PUT /research/{decision-rule|judge-rubric}` write their files. The API never commits; the lead commits the files.
- The seed map. `conditions/seeds.yaml` is made by a script and changed in git only. `GET|PUT /conditions/seeds/file` is 404, and `POST /seeds/generate` is not built.
- In the contract but not built yet (answer 501 `not_built`; `app.NOT_BUILT` is the list, and a test checks it against this file): `GET /budget`, `POST /scenarios/{scenario_id}/generate-news`, `POST /prompts/preview`, `GET /presets`, `POST /presets`, `GET /presets/{preset_id}`, `POST /runs/{run_id}/clone`, `GET /runs/compare`, `GET /evaluations`, `POST /evaluations`, `GET /evaluations/{evaluation_id}`.
